GoHustlr payments: what the audit found, and how to fix it without breaking anything

Two multi-agent audits covering every Stripe money path, the fee and incentive arithmetic, the controls engine, and the admin money authority. No production system was touched. Nothing has been fixed yet — this is the plan.

72findings surviving adversarial refutation
14severe, after cross-workflow dedup
6root causes behind nearly all of them
494existing tests, all passing

The verdict

The core escrow path is genuinely well built. No agent found a way to create money, steal platform funds, or charge a party an amount they never agreed to on the main flow — and several tried hard. Nothing found is extractable as cash by an outside attacker. The losses are forgone margin, misreported budgets, unpaid workers, and detection you cannot trust.

But the money layer is not ready for the live-key cutover today. The problems cluster in the two subsystems built most recently and defended least — tips and promotions — plus a set of detectors that report green while watching nothing.

The single worst thing found

A migration that meant only to re-anchor a control's clock silently deleted two predicates from ctl_escrow_hold_expiring_work_done, removing the entire population it exists to watch: an earner who did the work, marked it done, and is 24–48 hours from the escrow hold being voided with nothing left to capture. It is live today, it costs the full gig value per event, and every hourly sweep reports it healthy.

I verified this one by hand. The original required coalesce(b.earner_done, false) and matched b.status in ('confirmed','completed'). The live version dropped the earner_done predicate outright and swapped 'confirmed' for 'verified' — but a verified booking has already been captured, so p.status = 'authorized' can never hold for it. The ghosted-poster case the control was written for is now excluded twice over.

The runner-up is the tip rail. Tips carry no application fee, route 100% to the earner's connected account, and pay out daily. Their three caps are all bypassable by simple concurrency — the check is a lock-free read in one transaction and the charge happens in the next — and the over-cap money rolls back its own ledger row on the way out, so the cap never tightens. Separately, a refunded or charged-back tip is reversed nowhere: no ledger, no dispute row, no console path. The drift control that should catch it instead certifies the inflated balance as correct.

Six root causes, not seventy-two bugs

This is the part that matters for planning. The findings are not independent defects to be worked through one at a time — they are six systemic patterns, and fixing the pattern is what stops the next one.

Cause 01 · Structural

create or replace drift

Money functions are redefined across many migrations and only the last definition in timestamp order is live. pin_booking_amount is redefined nine times. A later rewrite that silently drops a guard from an earlier one is invisible to code review, to the test suite, and to every control.

This caused the worst finding (the gutted control) and the highest-value one (settle_booking_benefits never receiving the kind filter its sibling function got). It is also exactly the class that produced the July audit's critical escrow drain. This is the one to fix structurally, first.

Cause 02 · Concurrency

Check-then-act across an I/O boundary

A guard reads state in one transaction, then a Stripe round-trip happens, then a write lands in another. Every instance is bypassable by firing two requests in parallel.

  • Tip caps: headroom is read, committed, then the card is charged.
  • accept-booking vs stripe-cancel-payment: a confirmed booking behind a dead hold.
  • Two concurrent captures at different percentages race the pre-capture split write.
  • The promo-code rate limiter is select count(*) then if.

The codebase already knows the right pattern — consume_promo_grant makes the increment be the check in a single conditional UPDATE. It just was not applied uniformly.

Cause 03 · Ledger

Everything that reverses money is keyed on the payments table

Tips live in tip_ledger, referral bonuses in bonus_ledger, credits on the booking pin. None of them has a payments row — so recordReversal, reconcile-stripe, and admin-payment-action are all structurally blind to them. There is no console path to reverse a tip at all, and an operator told to "reverse the tip" will instead refund the escrow charge and claw back the earner's job pay.

Cause 04 · Detection

Controls that cannot fire, reporting green

Four separate detectors are structurally incapable of firing: the gutted escrow control; ctl_stripe_id_mode_mismatch (gated on an app_flags key no migration creates, and with length predicates that match every real Stripe id); the admin login throttle (which has zero callers, so no lockout exists at all despite being documented); and the alert-dispatch path, where turning the flags off kills all alerting permanently with nothing watching. A control that cannot fire is worse than no control, because it certifies health.

Cause 05 · Accounting

Budget accounting measures the wrong quantity

Three defects each write both sides of the ledger consistently wrong, which is why no existing bookkeeping-vs-bookkeeping control sees them: settle_booking_benefits refunds every delivered poster discount back to its own campaign at capture; max_benefit_cents clamps what a campaign is charged while the discount it delivers stays uncapped; and promo cost is measured against the standing rate, blind to the loyalty tier. Real give-away exceeds the declared budget by 2× to 4.73× while the burn-down bar reads near zero.

Cause 06 · Hygiene

Console audit and authorization gaps

Five console surfaces write their audit row after the mutation, so a committed change is reported to the operator as a failure and leaves no record. /promotions — the only budget-spending surface — has no MFA step-up while every comparable surface does. addTeamMember can strand the console with no admin.

The remediation plan

Ordered by dependency, not by severity. Deploy vectors: MIGRATION supabase db push --linked · EDGE FN supabase functions deploy <name> · CONSOLE cd admin && npx vercel --prod (never auto-deploys) · CLIENT app release · CONFIG dashboard or flag only.

Phase 0 Make the tests and the detectors trustworthy first — before any behaviour change

Nothing after this is verifiable until it lands: every later fix needs a working detector to confirm it, and four detectors are currently lying. This phase is monitoring and tests only — zero application behaviour changes, so it is also the lowest-risk thing to ship.

  1. Add a finalDefinition(fnName) test helper that walks supabase/migrations/ in filename order and returns the last definition of a SQL function. Route every existing SQL assertion through it. A test that reads a named migration file is testing a dead body. TEST ONLY
  2. Add controlPopulation.test.js — for every ctl_* function, assert that any load-bearing token present in any definition (earner_done, 'confirmed', 'captured', for update, budget_cents, resolved_at) survives into the last one. The audit ran this logic against the current tree: one violation, zero false positives across 41 other controls. TEST ONLY
  3. Add the same drift guard for money functions — a dropped raise exception, clamp, .eq() predicate, or revoke between successive definitions fails the build. TEST ONLY
  4. Restore ctl_escrow_hold_expiring_work_done, add an anchor-independent ctl_work_done_never_paid, and add controls.fn_body_sha + ctl_control_body_drift so a silent rewrite pages a human. MIGRATION
  5. Wire the admin login throttle and add ctl_admin_login_not_recorded. MIGRATION CONSOLE
  6. Add ctl_alert_not_dispatching plus a dispatch liveness log and a 24h expiry on the two alerting flags only. MIGRATION CONSOLE
  7. Repair ctl_stripe_id_mode_mismatch — replace the shape heuristic with a provenance check, seed the missing flag, add controls.requires_flags + ctl_control_dependency_missing. MIGRATION
  8. Raise the controls_digest pg_net timeout to 120s. Do this before items 4–7 land, or the daily false HIGH competes with real findings. MIGRATION

Hazard — item 5 is the realistic failure. gohustlr-admin does not auto-deploy. Pushing the migration without running npx vercel --prod reproduces the exact bug it fixes. The new control is deliberately written to fire on that half-deployed state.

Hazard — re-keying entity_id in item 4 will auto-resolve existing findings with a misleading "no longer returned" note. Resolve them explicitly in the same migration with a truthful note; the real violations reopen under booking ids within the hour.

How each fix gets verified

Per fix, in this order

  1. Write the failing test first, against unfixed code, and watch it fail. A test written after the fix proves only that the code does what it does. This is not ceremony — several findings here exist because a green test was examining the wrong thing: tipCaps.test.js has twelve passing tests asserting "checked before the charge" and "the caps are serialised," both true, and neither catches the concurrency bypass, because they examine two transactions in isolation.
  2. Pin the wrong answer by value. Where the bug is arithmetic, assert the specific broken number (promoBenefitCents(20000, 1000, standing=1000) === 0) so a revert cannot be made to pass by editing the mirror alongside the code.
  3. Apply the fix. Test passes.
  4. Full suite green — 494 is the floor, and it must not drop.
  5. For SQL, assert against finalDefinition(), never a named file.
  6. Diff the security-relevant state before and after: enabled controls, admin roles, RLS policies, function grants. The July round taught this the hard way — damage is not always where the change said it was.

Budget for fix-induced regressions

The July 2026 audit fixed 54 findings and introduced 7 regressions doing it — a 13% rate. With ~70 findings here, expect roughly 8–9. Plan a dedicated review pass on the diff itself after each phase; do not treat it as optional. Two of the findings in this report are regressions introduced by earlier fixes.

The environment constraint

There is no Docker on this machine, so a local Supabase instance is not available and migrations cannot be dry-run locally. Runtime verification needs one of:

  • A Supabase branch database (cloud, no Docker) — the right home for anything that must actually execute SQL, and the only safe place for the adversarial simulations.
  • Stripe test mode for the end-to-end money flows — which is where you already are, so this costs nothing.
  • Static assertion via the migration-parsing test convention for everything else. This is why the finalDefinition() helper is Phase 0 item 1: without local SQL execution, parsed-off-disk tests are the primary defence.

The re-audit

After each phase, three passes — each catching something the others structurally cannot.

1 · Fix verification

One agent per fixed finding, given the original finding and the diff, asked to prove the specific failure is now impossible. Paired with an adversarial agent asked to reach the same outcome by a different route — fixes frequently move a bug rather than close it, and the original finding text is exactly the wrong thing to search against.

2 · Regression hunt on the diff

Scoped to the changed lines and their callers, not the whole repo. This is the pass that catches the 13%. Specifically instructed to check whether any create or replace in the fix dropped a guard from the definition it replaced — the drift class that caused two findings in this report.

3 · Full re-run of both audit workflows

The scripts are saved and re-runnable. Invoke them fresh — do not pass resumeFromRunId. Resume replays cached results for unchanged prompts, and since the prompts will not have changed but the code will have, a resumed run would confidently report the old findings against the new code.

Read-only, always

Every audit agent ran with an explicit read-only constraint: no supabase/psql/stripe CLI, no HTTP to any endpoint, no forged JWTs, no edge-function invocation, no repo writes. This is not caution for its own sake — a round-1 agent in a previous audit disabled a live security control through the console and it stayed off for hours, unnoticed, because a disabled control reports neither errors nor staleness. Keep the constraint on every future round. Anything that must mutate belongs on a branch database.

What is sound — do not churn these

Attacked and held

  • The Stripe processing floor in platform_fee_cents — max(round-half-up(a×bps/10000), ceil(a×0.029)+30+25), capped at the amount, bigint-widened. The single load-bearing guard in the money layer: it makes self-dealing cost ~3.2%, means a 0% promotion never settles at a loss, and caps what a fee credit can ever be worth.
  • The three immutable pins at booking INSERT and their inheritance by payments. Capture idempotency genuinely follows from deriving only from immutable values — the fee × pct² retry hazard is closed, and a rate change provably cannot re-price agreed work.
  • consume_promo_grant's increment-is-the-check UPDATE and the two stacking unique indexes. The mechanism is correct; Phase 2 fixes what it counts, not how it counts.
  • Vest-on-outcome for referrals, delivered as credits rather than cash. It genuinely defeats the non-working farmer.
  • guard_bookings_write's completed → verified gate requiring a captured payment — this is what turns several defects above into "stuck" rather than "settled without payment."
  • No RLS or IDOR gap was found on any money table or endpoint. Every defect in this report requires either a legitimate role or an unlucky ordering — never a privilege bypass. Grants discipline on money RPCs is applied consistently.
  • The controls framework itself — functions rather than stored SQL text, fn_name validated against both a regex and pg_proc, findings unique per (control_key, entity_id) with auto-resolve, config in app_flags rather than a GUC. The failures are in individual predicates, not the engine.
  • reconcile-stripe — authenticated on a rotating shared secret, fails closed, and its checks 1, 4 and 5 are real working hourly detectors that backstop several findings above.
  • __tests__/pricing.test.js parsing the migration off disk. This is the right pattern and it works — Phase 0 generalises it rather than replacing it.

Open questions only runtime can settle

All runnable in Stripe test mode or a branch database. None requires touching production.

  1. Is the full event set registered on the live webhook destination? The highest-leverage unknown in the report. Test-mode registration does not carry over, and payment_intent.canceled is the only thing currently healing the accept/cancel race. Verify before any real earner works a gig.
  2. Has any poster_discount campaign already run? The settle bug corrupts spent_cents historically. Read-only check: if spent_cents is near zero with a non-zero redemptions_used, that campaign has already overspent and needs an audited recompute. No blind backfill.
  3. Does Stripe Radar throttle a concurrent off-session tip burst? It could reduce the multiplier — but a bypass whose bound is "whatever Radar allows" is not a $200 cap, so this does not change the fix.
  4. Does GoTrue record failed password grants? The shape of the login-throttle fix depends on it. Either way the throttle still needs wiring — an audit log cannot block.
  5. The real Stripe account and customer counts. Two docs disagree (7 and 4 vs 7 and 3), and this is the population that breaks at cutover.
  6. The true out-of-pocket on a partial capture with a full fee credit — derived algebraically at 2–3c; worth observing once.
