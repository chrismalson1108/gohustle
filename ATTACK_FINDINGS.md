## [high] Capture writes the money split to `payments` BEFORE the Stripe call with no status predicate — two overlapping captures make `credit_earnings` credit the wrong number, and no SQL control can see it

- **Upgrade-related:** False
- **Attack:** The claim "capture is idempotent because the fee derives only from immutable inputs" is half true: amount_cents / fee_bps / fee_credit_cents / poster_discount_cents really are immutable (verified in live pg_proc — `pin_payment_fee_bps` re-pins all three to OLD on UPDATE, and `payments` has only SELECT policies so no client can touch it). But `pct` is a caller-supplied input, and it is written into the shared `payments` row before the irreversible Stripe call, guarded by nothing.

Ordering in stripe-capture-payment, both branches: (1) `update({fee_cents, earner_amount_cents}).eq('id', payment.id)` — no `.eq('status', …)`, no CAS, no single-flight claim; (2) `stripe.paymentIntents.capture(...)`; (3) `update({status:'captured'})`; (4) `rpc('credit_earnings')`. Compare accept-booking/index.ts:88, which does use `.eq('status','pending')` as a compare-and-swap, and `credit_earnings` itself, which claims via a conditional UPDATE. The capture path has neither.

Attack: the poster fires two captures on their own booking with different `pct` (curl with their own JWT; or a UI double-submit where the second pass uses "report a problem"). Interleave R1(pct absent → full) and R2(pct=0.5):
  R1 writes FULL split → R2 writes REDUCED split → R1 captures the FULL hold at Stripe → R1 writes status='captured' → R1 calls credit_earnings, which reads the row and credits the REDUCED figure → R2's capture then throws payment_intent_unexpected_state and 500s.
The reverse order (R1=0.5, R2=full) produces the mirror image: Stripe captures 50%, the ledger records 100%.

The same shape is reachable without concurrency whenever Stripe captures but the HTTP call errors back (timeout): attempt 1 at pct=0.5 leaves the reduced split written with status still 'authorized'; the poster retries at 100%, which rewrites the FULL split and then 500s on the already-succeeded capture; the delayed payment_intent.succeeded webhook then flips status to 'captured' and credits the FULL figure against a 50% capture.
- **Wrong result:** Stripe and the ledger disagree about the same capture. Under-credit case: the earner's connected balance receives the full net, but `payments.earner_amount_cents`/`fee_cents` and `profiles.earnings_today/week/total` record ~50% — the Transactions screen and the Tax Center year-end CSV understate the earner's actual 1099 income, and `admin-payment-action`'s refund ceiling (`earner_amount_cents + fee_cents`, index.ts:153) is computed from the same understated pair, so an operator cannot refund the poster more than half of what the poster actually paid. Over-credit case: GMV, platform fee revenue and the earner's reported income are all overstated.

Critically this is invisible to every SQL control. `ctl_payment_ledger_impossible` (read from live pg_proc) only flags `captured_total > amount_cents`; an equal-or-smaller total passes. `ctl_earnings_total_drift` (live pg_proc) computes `expected` as `sum(payments.earner_amount_cents) where earnings_credited` — i.e. it compares the profile to the very row that is wrong, so it stays green. The only detector is reconcile-stripe's `captured_total_mismatch`, which scans payments created in the last 14 days, limit 200 — after that window the discrepancy is permanent and unfindable.
- **Claimed evidence:** supabase/functions/stripe-capture-payment/index.ts:188-191 (partial branch pre-write, `.eq('id', payment.id)` only), :192-195 (Stripe capture), :196-199 (status write), :209-212 / :213 / :214-217 (full branch, identical shape), :227 (`rpc('credit_earnings')`). Live pg_proc `ctl_payment_ledger_impossible` (only `captured_total_cents > amount_cents`) and `ctl_earnings_total_drift` (expected = sum of `payments.earner_amount_cents`).
