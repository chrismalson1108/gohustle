# GoHustlr — full-system audit, 2026-07-30

Branch `security/audit-2026-07-30`. Baseline `2c3e7ce`.

This round differs from the previous ones in one way that matters: **the apps were
actually run.** Web on the dev server and mobile in the iOS simulator, signed in to
the same account at the same moment, side by side. Most of what follows was found by
looking at a screen, not by reading a file — which is why it is mostly money and
safety defects that static review had passed over six times.

**On #19** — both delete paths lean on FK cascade for anything they don't purge by
hand. `support_tickets.user_id` is `on delete set null`, so the ticket deliberately
outlives the account — but the table also denormalises `email` (not null) and `name`,
which that cascade never touches. A deleted user's plain email address and real name sat
in the support queue indefinitely, with the profile link nulled so nothing even explained
whose they were.

I swept every `on delete set null` reference to `profiles` rather than fixing just this
one. **`support_tickets` was the only survivor holding direct identifiers.**
`client_errors` keeps technical fields (platform, message, context) and `reports` keeps a
moderation record — both survive by design with no direct identifier. The residual is
`support_ticket_messages.body`, free text the user typed: scrubbing it would gut the
support record, which is a retention-policy call rather than a code one.

**On #16** — the fail-open design around it is deliberate and correct: the other paths
allow on failure because the failure is a *system* condition (Claude down, network
stalled) a user cannot arrange, and blocking every upload during an outage is the worse
trade. Size is attacker-chosen. That is the brief's own test — *can a user induce the
failure?* — and it is what separates a bypass from a degradation.

**On #17** — suspension is the safety kill switch, used when someone is believed to be a
risk to another user. `messages_insert` is party-scoped, so the people a suspended
account could still reach were exactly its existing booking counterparties: the person
who most likely just reported them.

**On #15** — the two branches of the same guard disagreed about which columns are
server-owned. `started_at` is the one that costs money: two independent controls refuse
to release a poster's hold once it is set (`trg_guard_started_booking_cancel`, and
`stripe-cancel-payment`'s 409), and neither asks *when* it was set. An earner books with
it already stamped; the row is forced to `pending` so nothing looks wrong; the poster
accepts and the hold lands on their card — and from then on they can neither cancel nor
release it. It sits authorized until Stripe expires it ~7 days later, and the only route
left is a dispute, which has no adjudication path. Every pinned value equals the
column's own default, so an ordinary booking INSERT is unchanged.

**On #14** — the one that would have cost someone real money. Both delete paths
refuse to run while a booking is `confirmed`/`completed`, because cascading those rows
voids the hold and leaves the earner unpaid with no record. Both computed that refusal
from `.select()`s whose `error` was thrown away; Supabase returns `data: null` on
failure, so `earnerUnsettled?.length ?? 0` became `0`, the guard passed, and the
irreversible cascade ran. The control disappeared precisely when it could not verify
anything. The report check three lines below already failed closed
(`REVIEW_CHECK_FAILED`) — the escrow check just never got the same treatment.

**Note on #12:** that was a defect I introduced two commits earlier, caught by driving
the app again after my own change. #11's first cut also rendered `$-12.50` instead of
`-$12.50` and was caught by its own test. Budgeting a hostile pass over one's own work
is not optional advice.

## 3b. Confirmed but not fixed — ranked, for the next pass

The one I would do first:

**Image moderation is optional.** `moderate-image` authorises correctly and now fails
closed on size (#16), but *nothing requires it to be called*. It is invoked by the two
clients after upload; a patched client, or a direct Storage API call with the user's own
token, stores an image that is never scanned at all. Hardening the scanner does not help
when calling it is voluntary. The fix is architectural — a Storage webhook or a
moderation gate between upload and the row that publishes the URL — which is why I did
not attempt it inside this pass.

Then, roughly in order:
- **Blocking does not stop booking-row writes** — a blocked counterparty retains write
  access to a shared booking, and those writes generate notifications.
- **Reviews, application notes, amendment notes and certifications run only the keyword
  layer**, not the AI pass the gig text gets.
- **Account deletion reports success when storage removal fails**, and its pagination
  loop aborts early — so objects can survive a "successful" deletion.
- **`bookings.slot_label` is pinned by neither branch** of `guard_bookings_write`, so the
  poster can rewrite the agreed time label after the fact.
- **`certifications_insert_own` pins only `user_id`**, leaving `image_url` unchecked.
- Assistant earnings plan reports gross against a take-home goal; mobile `JobCard` can
  render an unrounded float as a price; `moderate-text` truncates at 4000 chars while gig
  descriptions are uncapped; admin renders poster-controlled `jobs.photos` into
  `href`/`src`; the saved-search notifier can put attacker text in a blocker's Alerts;
  and five small mobile/web UI defects (delete modal has no escape, settings search no
  longer finds deletion, the challenge-complete toast is overwritten before it renders,
  web seeds 5 of 27 badges, `safety-alert` links to a route that does not exist).

The 17 split-verdict findings are in the workflow journal. I did not act on any of them:
one refuter each judged them wrong, and at a 32% refute rate a single dissent is reason
to look again rather than to patch.

## 2. Verified NOT to be problems (negative results worth recording)

- **Browse works under an authenticated session.** The §6.9 brief flagged the rewritten
  `jobs_select_all` as never having been observed live. It returns 3 gigs. Anon getting
  `permission denied for table jobs` is correct hardening (revoked in `20260710020000`),
  not an outage — the marketing page uses static content and Browse is auth-gated.
- **Every admin server action is individually gated.** All five action files route
  through `requireAdmin`, and that chain verifies an authentic `getUser()`, AAL2 read
  from the JWT, `admin_users` membership, then tier. No ungated action exists.
- **No migration drift.** Every tracked migration is applied remotely, in order. This
  answers an open question in `KNOWN_RISKS.md` §7.1/§6.2.
- **No secret is committed.** The one commit matching a service-role assignment
  (`e8f970c`) contains placeholder examples (`<service_role secret>`). No `.env` tracked.
- **Settings does not wipe the profile.** Form loads fully populated; the earlier fix holds.
- **Live probes: 82/84.** The two non-passes are correct behaviour (anon denied on
  `jobs`; `stripe-webhook` returning 400 "Missing signature"). Re-run after both
  migrations and the function deploy — identical, so nothing regressed.

### Refuted

## 3. Found and NOT fixed — needs an owner decision

**Off-platform image URLs are unconstrained.** `profiles.avatar_url` and `jobs.photos`
have no host or path guard anywhere in the tree — unlike `chat-photos` and
`completion-photos`, which both have one. Anyone can point their avatar at
`https://attacker.example/x.png` and collect the IP address, coarse location and
view-time of every user whose device renders it. On a product where strangers arrange
to meet in person, that is a real privacy leak, not a theoretical one.

I did not ship the fix. The obvious version — constrain to the project's storage host —
is the right shape (OAuth sign-in populates only `name`/`avatar_initial`, never
`avatar_url`, so there is no legitimate off-host source), but I could not query
production to confirm no legacy row would be rejected, and could not test an avatar
upload without writing to the live database. Shipping a constraint that breaks avatar
rendering would be worse than the bug. **Recommended:** check the distribution of
`avatar_url` / `jobs.photos` values first, then add an UPDATE-time guard that fires only
when the column changes — the same pattern `guard_job_pay_floor` uses, so legacy rows
stay readable.

**A poster can re-price a gig after someone applies, before accepting.**
`guard_jobs_write` pins `pay`, `pay_type` and `estimated_hours` hard once a booking is
live — but "live" is `confirmed`/`completed`/`verified` only, so a `pending` application
does not lock the price. An earner applies to a $100 gig; the poster edits it to $40 and
then accepts; the hold is placed at $40. The earner is not trapped (they can walk from a
pending booking, and their own screen shows the new number), so this is bait-and-switch
exposure rather than escrow theft — and the $10 floor now bounds how far it can go.

I did not change it, because the obvious fix is worse than the bug: adding `pending` to
that set means one stale applicant permanently prevents a poster from correcting their
own price, and applications can sit pending indefinitely. Excluding `pending` looks
deliberate. The clean fix is to snapshot the agreed rate onto the booking at INSERT —
the way `starts_at` is already snapshotted from the slot — which is a schema change
across three write paths, not a guard tweak. **Your call.**

**Credential scans are bulk-harvestable in one query — but showing them is the
feature.** The `certificates` bucket is public (`buckets … true`), and
`20260725000000` closed `/object/list` enumeration with an owner-scoped policy. The
`certifications` **table**, though, is `certifications_public_read USING(true)` and
holds `image_url`. So a single unfiltered `GET /rest/v1/certifications?select=image_url`
returns the path of every credential document in the system, and each is then fetchable
from the public bucket.

I am **not** treating this as a straightforward leak, and the finding that raised it
overstated the case. `/u/[id]` — the page you land on when viewing someone else — calls
`fetchCertifications(id)` and renders those images on purpose. Certifications are a
trust signal you publish to prospective clients; other users seeing them is the product
working as designed.

The real residual is narrower and worth a decision: the storage lockdown stopped anyone
*walking the bucket*, but the table still allows one request to return all of it. For
driver's-licence and certification scans, "viewable one profile at a time" and
"downloadable in bulk" are different risks. The question for you is whether the scan
itself should ever be public, or whether the claim (title / issuer / year) is the public
part with the document reserved for admin verification. That is a product call, so I
left it alone — but note the `profiles` column-lockdown pattern is the template if you
want it.

**Live data violates a stated invariant.** A `$20,000` gig exists (double `MAX_JOB_PAY`)
and is unpayable — escrow rejects anything over `1_000_000` cents, so an earner can book
it and the poster's authorization fails at accept time. The ceiling is now enforced for
new writes, but that row is still live and still skewing Market Insights. Removing it is
a data decision, not a code one.

**A gig with zero slots is live.** `isJobBookable` deliberately fails OPEN on an empty
slots array because "PostJob/EditJob always attach at least a Flexible slot". Production
contradicts that — one gig shows "No times available" and cannot be booked. Worth finding
out how it was created.

**One unresolved report indefinitely blocks payment for completed work.**
`earner-claim-payment` refuses to auto-settle while any unresolved, non-auto report
exists on the booking. That gate is *right* — an open safety allegation should pause an
automatic payout, and it correctly excludes `source='auto'` content flags so a moderation
hit can't strand a payout.

The problem is the asymmetry it creates given `KNOWN_RISKS.md` §5.2: a poster who does
not want to pay can file one report, never resolve it, and the earner's only
self-service route to being paid for work they actually did is closed for as long as
nobody adjudicates. Filing costs nothing, one is enough, and there is no SLA on the
other side.

This is not a new defect — it is §5.2's missing adjudication path, and I am recording it
because it is the concrete harm that gap enables rather than an abstract one. It is
partly self-limiting (the report lands in the moderation queue, so the abuse leaves a
trail, and an admin resolving it releases the claim), which makes **response time** the
actual control. Worth a named owner and a target turnaround before beta.

**Flexible gigs have no self-service payout path, and the earner is told nothing.**
`earner-claim-payment` returns `NO_SCHEDULE` → "contact support" when the slot has no
`starts_at`, which is deliberate. But `canClaimEarnerPayment` returns false in the same
case, so the button never renders and the earner never sees that guidance — they get
silence. This is the known-open ghosting gap, not a new hole, but the client should
surface the support route.

**Web and mobile disagree on what a conversation list is.** Web shows a row per booking
(7, with a "Say hi 👋" placeholder); mobile shows only bookings that have messages (4).
Both are defensible; they should not differ. Product call.

**Ambiguity, not a bug:** the "Earn $100 This Week" challenge counts gross gig value at
mark-done, while every other earnings surface counts fee-net at payout — so one screen
shows `40/100` and `$36` for the same week. The copy says "Complete gigs *totaling*
$100", which makes gross defensible. Worth deciding deliberately.

**Minor:** the DOB picker offers birth years 2026–2009 on a product that states 18+.
Client validates with `isAdult()` and the server enforces independently
(`guard_min_age`, and `date_of_birth` is write-once), so this is polish, not a hole.

**Report flooding, characterised accurately:** `log-moderation` permits 20 auto-reports
per user per 5 minutes (240/hr). Because it writes `reported_user_id: user.id`, an
attacker can only flood reports *about themselves* — admin-queue noise, not a way to
frame a victim. Worth tightening; not a hole.

## 4. What was NOT exercised, and why

Stated plainly, because claiming coverage one does not have is worse than the gap:

- **No authenticated REST probes.** Reading the session token out of browser storage was
  correctly refused by the sandbox, and I did not work around it. Authenticated RLS
  behaviour therefore rests on code review plus what the app itself exercised, not on
  direct API calls.
- **No end-to-end money loop.** Booking, accepting, escrow, capture, tip and refund were
  not run, because every one of them writes to the production database. Stripe is in
  sandbox so no real money was at stake, but the data would have been real. The seed
  scripts (`scripts/seed-dallas.mjs`, tagged `@seed.gohustlr.test`, with
  `wipe-seed.mjs`) are the sanctioned path and need your go-ahead.
- **The pay ceiling's rejection path was not fired.** The guard is deployed and the
  read path is verified unaffected, but triggering the rejection means posting a gig
  over $10,000 in production.
- **Admin console was built and gated-by-inspection, not driven.** It requires an admin
  login with MFA.
- **The audit's own verification is unfinished.** 72 findings were raised across 15
  dimensions; the adversarial pass was ~69/144 verdicts when this was written and is
  still running. Items in §3 are ones I confirmed myself, by hand, against current code.
